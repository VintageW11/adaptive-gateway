Auto activity detection — methodology and formulas

When the dashboard profile is set to Auto, the gateway does not pick a VPN directly from the packet stream. It first guesses what the user is doing, maps that guess to one of four traffic profiles, then runs the usual SAW ranking with that profile’s weights. This note is the live classifier in classify_from_signals / classify_device / auto_hysteresis_need.

In simple terms: Auto is a two-step process. Step 1 looks at how busy the line is and whether the traffic looks like browsing, a call, a video, or a download. Step 2 is the same SAW formula as the rest of the paper: whichever VPN scores highest under that activity’s weights is the one that is used.

1. Two-layer decision

  1. Measure this device’s rate, upload/download mix, UDP vs TCP, and (when available) DNS / CDN destination hints.
  2. Score four activity votes Vbalanced, Vgaming, Vstreaming, Vdownloads.
  3. Take the winner as a candidate profile pguess.
  4. Hold that guess through hysteresis (a few ticks / a short gap) so one burst does not flip the UI.
  5. Commit p* and rank VPNs with SAW using weights w(p*).
p* = hysteresis( arg maxp Vp )
i* = arg maxi Si( w(p*) )

UI names: Everyday browsing = balanced, Gaming & calls = gaming, Video streaming = streaming, Big downloads = downloads.

In simple terms: Auto never invents a fifth SAW formula. It only chooses which of the four weight vectors to plug in. Fail, affinity, and live ping metrics stay exactly as in the SAW write-up.

VPN hairpin (PC → Ubuntu tunnel → Internet) often looks idle on the MikroTik mangle counters. If the house WAN is in the video band, Auto may copy that house rate onto this PC:

house_pull ↔ 0.22 ≤ agg < 6.0

Copy is skipped when Discord-like names are present, there is no video-CDN evidence, and agg < 0.45 Mbps (chat must not be treated as YouTube). Otherwise, if this is the sole / only-busy client, or QUIC / CDN is visible:

r ← max(r, agg), rx ← max(rx, agg)

Host-wide Auto (the dashboard “Right now” line) uses the same classifier with house WAN rate. If every known LAN client is idle and agg < 0.22, it forces Everyday browsing so leftover DNS cache cannot keep Video streaming on.

In simple terms: Auto looks at how many megabits are moving, whether they are mostly coming down or going up, and whether the packets are UDP (games, calls, HTTP/3 video) or TCP. Names such as googlevideo or discord.media can confirm the guess, but they are not shown on the dashboard. If your PC’s traffic is hidden inside a VPN, Auto may borrow the whole-house download rate so YouTube still counts as video.

3. Shape tests (the boolean rules)

Rates are in Mbps. All of the following are evaluated every engine tick (~a few seconds).

idle ↔ r < 0.08  ∧  Nudp < 2  ∧  ¬bidir
video_like ↔ 0.22 ≤ r < 6.0
download_heavy ↔ rx ≥ 0.22  ∧  rx > 2.5 max(rtx, 0.01)
upload_heavy ↔ rtx ≥ 0.2  ∧  rtx ≥ 0.35 rx
bulk ↔ (r ≥ 8  ∨  bulk_sustained)  ∧  ¬video_cdn

bulk_sustained is true when at least two recent house-rate samples are ≥ 6 Mbps. play_floor = 0.22 Mbps (something is still being pulled, not just a leftover tab name).

Interactive / call-shaped traffic (used for Gaming & calls when no video is winning):

call_like ↔ ¬idle  ∧  r < 6  ∧  ( (bidir ∧ (Nudp ≥ 2 ∨ u ≥ 0.2)) ∨ (Nudp ≥ 3 ∧ r ≥ 0.08) )
metric_game ↔ ¬idle  ∧  r < 0.6  ∧  (UDP mix with Nudp ≥ 3 and/or bidir)

QUIC without bidir and with Nudp < 3 is not treated as a game/call (that is typical YouTube HTTP/3).

In simple terms: Quiet line = browsing. A steady one-way download around a few Mbps = video-shaped. Lots of UDP going both ways at a modest rate = a call or a game. A very fat transfer (about 8 Mbps or a sustained 6+ Mbps) = a download, unless a video CDN is already in play. Chat in Discord is mostly HTTPS and does not look like a call; a real voice session or Go Live does, because it uses two-way UDP or a heavy upload.

4. Watching vs calling (priority)

Video names (CDN keys such as googlevideo, nflxvideo, ttvnw) and destination-IP hints set pulling_video. A leftover site name (youtube.com, netflix, …) plus download_heavy sets leftover_site. Discord tray names (discord.com / discord.gg) are not a call; discord.media / rtc.discord / discord-gateway are.

Without a Discord app hint:

watching ↔ ((pulling_video ∨ leftover_site) ∧ r ≥ 0.22 ∧ ¬upload_heavy)  ∨  (video_like ∧ ¬download_hit)

With a Discord app hint, chat-plus-tabs must not count as video. Watching requires a clearer pull:

watchingDiscord ↔ r ≥ 0.45 ∧ ¬upload_heavy ∧ (pulling_video ∨ leftover_site ∨ download_heavy)

If Discord is on a real call / Go Live and there is no video CDN, watching is cleared so Gaming & calls can win:

if Discord ∧ (live_call_udp ∨ golive) ∧ ¬pulling_video then watching ← false
golive ↔ upload_heavy ∧ r < 8 ∧ ¬video_cdn

Call activity (only if not already watching or bulk):

call_active ↔ ¬watching ∧ ¬bulk ∧ ( (real_call_DNS ∧ call_like) ∨ (Discord ∧ (live_call_udp ∨ golive)) ∨ (golive ∧ live_call_udp) )

In simple terms: YouTube playing beats leftover game or chat names. Discord sitting in the tray with other tabs open stays Everyday browsing. Discord voice or screen share (Go Live) goes to Gaming & calls. If you are actually watching YouTube at the same time as Discord, video still wins because the CDN pull is visible.

5. Vote scores

Start from Everyday browsing as the default:

Vbalanced = 1,  Vgaming = Vstreaming = Vdownloads = 0

If watching:

Vstreaming ← Vstreaming + 2 + 8·[video_cdn] + 4·[sticky_stream] + 2·[QUIC] + 4·[video_like ∧ ¬download_hit]
Vgaming ← 0  (watching zeros the game vote)

Else if bulk:

Vdownloads ← Vdownloads + 6 + 4·[download_DNS]

Else (interactive / light):

Vgaming += 6·[call_active] + 6·[real_game ∧ ¬idle] + 1.2·[weak_game ∧ 0.08 ≤ r < 0.6] + 6·[metric_game]
+ 1.5 if a game/call vote is already on and u ≥ 0.25 and Nudp ≥ 3
Vdownloads += 4 if download_DNS and r ≥ 1.5

Iverson brackets [·] are 1 when the test is true, else 0. Weak game DNS (for example a Steam tray name without matchmaking) only adds 1.2 — not enough alone to leave browsing.

Winner:

pguess = arg maxp Vp
if Vpguess < 2.5 then pguess ← balanced

In simple terms: Each activity gets points. Video can score from about 6 up to 16. A real call or in-game session scores about 6–13.5. A bulk transfer scores 6–10. Everyday browsing starts with 1 point and wins whenever nothing else reaches 2.5 — that is why idle, light tabs, and Discord chat stay on browsing.

6. Hysteresis (when the guess is allowed to stick)

The classifier runs every tick. The committed profile p* only changes after H agreeing ticks and a minimum gap G seconds since the last switch:

commit if hits(pguess) ≥ H(p*, pguess)  and  Δt ≥ G(p*, pguess)
From → toHits HGap G (s)Why
anything → Video streaming10Enter video immediately
Gaming & calls → Video streaming10YouTube while a call app is open
Video streaming → Everyday browsing10Drop video as soon as the pull stops
Video streaming → Big downloads28Do not confuse a 1080p spike with a file grab
anything → Gaming & calls28Need two ticks so leftover UDP is not a “call”
anything → Big downloads26Need a sustained bulk
non-browsing → Everyday browsing12Come back to idle after a short pause
any other pair26Default dampening

This hysteresis is per device (your PC vs a phone) and also on the host-wide Auto line. Switching the SAW winner still uses the committed p*, not the in-flight “leaning …” guess.

In simple terms: Video is allowed to turn on and off in one look, because a paused YouTube tab should not keep the streaming weights. Calls and downloads wait for a second look so a single UDP blip or speed-test spike does not move you. After that, SAW can change VPN.

7. How the profile switch changes the VPN

Committed Auto mode selects the SAW weight vector (Latency, Jitter, Loss, Throughput index, Reorder, MOS, MTU):

Auto modeWeights w (%)What the VPN ranking now cares about
Everyday browsing15, 15, 15, 15, 10, 20, 10Even QoS, MOS first — usually WireGuard
Gaming & calls35, 30, 10, 5, 5, 10, 5Latency + jitter — WireGuard / Nebula / IKEv2
Video streaming5, 10, 35, 25, 5, 15, 5Loss + throughput index — OpenVPN / SoftEther / IKEv2
Big downloads5, 5, 10, 40, 5, 5, 30Throughput index + MTU — SSTP / OpenConnect / OpenVPN

Then the SAW score is unchanged from the companion write-up:

S = Σk=17 nk wk + 0.03·(sec/5) + 0.03·(rel/5) + A
i* = arg maxi Si

A per-user Fail mark still does Sfail = 0.05 S on that path only; the tunnel stays up.

In simple terms: Detecting “Video streaming” does not mean “force OpenVPN.” It means “score every VPN as if loss and steady throughput matter more than ping.” Detecting “Gaming & calls” means “score them as if ping and jitter matter most.” The path with the best score under those weights is the one Auto switches to.

8. Worked examples

What you are doingTypical signalsGuess after votesThen SAW uses

YouTube / Netflix actually playing 0.22 ≤ r < 6, one-way download, often UDP/443 or googlevideo watching → Video streaming (1 tick) streaming weights
Discord voice or Go Live (no YouTube) bidir UDP or upload_heavy, discord.media / rtc call_active → Gaming & calls (2 ticks, 8 s gap) gaming weights
Steam download / large file r ≥ 8 or two samples ≥ 6, TCP-ish bulk → Big downloads (2 ticks, 6 s gap) downloads weights

In simple terms: Auto watches the shape of the traffic, not the app window. A quiet Discord window is browsing. A live call is gaming-weights. A playing video is streaming-weights. A big file grab is download-weights. After that, SAW still picks the VPN.
